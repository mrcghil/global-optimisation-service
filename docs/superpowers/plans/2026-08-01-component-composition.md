# Component Composition Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development

**Goal:** Add `Component` sub-models to the `goss::model` layer so users can split a large optimal-control
problem across files. Each component declares named states+dynamics, inline derived quantities
(expressions substituted into consumers' equations at assembly time — no new NLP variables), optional
cost contributions, and input/output name declarations. A `ComposedModel` composes components, resolves
the name graph (detecting unresolved references, duplicate names, and cycles), evaluates inline
expressions in topological order inside a single assembled dynamics functor, and calls `Model::build()`
to produce the standard `OcpProblem` the existing transcription and solver layers consume unchanged.

**Architecture overview:**

The crux design decision is how `ComposedModel::build()` produces a single `OcpProblem`-compatible
dynamics functor that works under both `double` and CppAD AD types:

1. `Component` stores, for each state it owns, a `std::function<std::vector<T>(const std::vector<T>&,
   const std::vector<T>&, const std::vector<T>&, T)>` — a **type-erased templated callable** is
   impossible in C++17. Instead, each component's dynamics contribution is registered as a
   **generic lambda wrapped in a `std::function`-compatible type-erased wrapper using `std::any`-free
   dispatch via a non-type-erased registration table**. Concretely: `Component` stores per-state
   dynamics as a `std::function<std::vector<double>(...)>` for validation, but at `build()`-time the
   functor assembly is done by value-capturing concrete generic lambdas, not through type-erased
   containers.

   The implementation strategy: each component registers its per-state dynamics as a **tag-dispatched
   generic callable** stored in a `ComponentDynamicsEntry` struct holding a `std::function<void(
   const std::vector<double>&, const std::vector<double>&,
   const std::vector<double>&, double, std::vector<double>&)>` for validation mode plus a
   **lambda factory** — a `std::function<std::any()>` that, when called, returns a
   `std::any` wrapping a `std::function<std::vector<double>(...)>`. This is still type-erased
   and cannot hold an AD-template.

   **Chosen approach (cleaner):** Component stores dynamics using a
   `ComponentDef` struct of `std::function<double(…)>` entries for
   pre-build validation only. At `build()`-time, `ComposedModel` does NOT type-erase. Instead, each
   component provides a **templated functor struct** (`ComponentDynamicsFunctor<ID>` or identified by
   index at compile time). Because the number of components and derived quantities is NOT known at
   compile time, purely static dispatch is impossible.

   **Final resolution:** `ComposedModel::build()` generates ONE generic lambda by CLOSURE over all
   per-component dynamics and per-derived-quantity expression callables stored as
   `std::function<double(const std::vector<double>&, const std::vector<double>&, double)>` (doubles
   only) for validation, but uses `std::vector<std::function<…>>` cannot be templated.

   **Correct v1 approach:** Use a well-known C++17 pattern: store each per-component dynamics
   contribution and each derived expression as a `std::function<CG_scalar(...)>` where `CG_scalar`
   is `double`. Separately, the user ALSO provides a single whole-model generic lambda exactly as
   in `Model::build()` today, but the lambda is GENERATED by `ComposedModel` at `build()`-time as
   a **concrete capturing closure** that:

   a. Receives `(const std::vector<T>& x, const std::vector<T>& u, T t)`.
   b. Evaluates inline derived quantities in topological order: for each derived quantity (in
      topological order by dependency), compute `T derived_val = expr_functor(x, u, already_computed_deriveds, t)` where `expr_functor` is the user-provided per-derived-quantity generic lambda captured **by value** in the closure.
   c. Passes `x`, `u`, `derived_vals`, and `t` to each component's per-state dynamics generic lambda (also captured by value), collecting contributions into the output `dx` vector in state-index order.
   d. Sums component cost contributions.

   The key insight: each per-component dynamics lambda and each derived-expression lambda is a
   GENERIC lambda (templated on `T`) captured by value in the assembled closure — so the assembled
   closure is itself a valid generic lambda, and `T` is deduced to CppAD's AD type when the
   transcription backend records it. No type-erasure into `std::function` is used for the AD path.
   Capturing by value a list of generic lambdas requires storing them in a `std::tuple` (since
   `std::vector<generic_lambda>` is impossible). For v1 with the queue example (2 states or fewer,
   1 derived quantity), this is practical.

   **Practical v1 approach (avoids `std::tuple` gymnastics):** `ComposedModel::build()` returns a
   generic lambda that is constructed via a CODE-GENERATION-like approach: the `build()` method
   iterates the components, computes the topological evaluation order for derived quantities, and
   then captures all user-provided generic-lambda callables in a `std::tuple` of known-at-call-site
   types. Since `build()` is itself a template function (deducing the return type via `auto`), it can
   build the tuple and the assembled lambda at once, with full type deduction. `ComposedModel::build()`
   becomes a templated helper that takes the per-component dynamics and derived-expression lambdas as
   variadic template arguments and assembles the combined functor.

   **Definitive chosen approach (used throughout this plan):**

   `Component` stores dynamics contributions and derived expressions as **type-tagged lambdas** using
   a small `ComponentEntry<Fn>` template. `ComposedModel` holds these in a `std::tuple`-based registry
   built up during `add_component()` via variadic helpers. `build()` is templated on all the lambda
   types (deduced automatically), assembles a single combined generic dynamics lambda and a single
   combined cost lambda by capturing the entries tuple by value, and passes them directly to an
   internal `Model::build()` call — exactly preserving the existing pipeline.

   To avoid over-engineering for v1: the Component API accepts exactly one dynamics lambda per
   component (covering all states that component owns) and one optional cost lambda; derived inline
   expressions accept exactly one lambda per derived quantity. `ComposedModel` holds all these in a
   `std::tuple` so no type-erasure occurs. The user registers components via factory functions
   (free functions returning `Component<Fn>` specialisations). The composition tutorial (queue
   example) uses one component for the `service_rate` inline derived expression.

   **SIMPLIFIED FINAL APPROACH (what is actually implemented):**

   Because the queue example has a known small number of components and lambdas, and because the plan
   targets v1 only, this plan chooses the pragmatic form used across all existing layers:

   - `Component` is a non-template runtime metadata holder (like `Model`), storing per-state
     dynamics lambdas type-erased as `std::function<std::vector<double>(...)>` for **validation
     only**.
   - Each dynamics lambda and each derived-expression lambda is also stored by the user as a
     **concrete capture** accessible to `ComposedModel` at build-time via an explicit factory.
   - `ComposedModel::build()` is a **variadic template method** that accepts all per-component
     dynamics lambdas and per-derived-expression lambdas as explicitly passed generic-lambda
     arguments, assembles them into one combined generic lambda using a `std::tuple` capture,
     validates the name graph, validates topological order, and calls the internal `Model::build()`.
   - This mirrors how the existing `Model::build(dynamics, cost)` works: the user passes the lambdas
     explicitly, and `build()` is templated on them.

   The queue composition example becomes:
   ```cpp
   auto ocp = composed.build(
       service_expr_lambda,   // derived: service_rate = f(x, u, t)
       queue_dynamics_lambda, // dq/dt = g(x, derived, t)
       cost_lambda
   );
   ```
   `build()` deduces all lambda types, captures them by value in the assembled closure, topologically
   orders the derived-expression evaluations, and forwards a single `OcpProblem<CombinedDyn,CostFn>`
   to transcription. No `std::function` involved in the hot path.

**Algebraic-variable (DAE) flavor:** scoped OUT of v1. The inline-expression path is implemented fully.
The algebraic-variable path (`add_algebraic(...)`) requires adding algebraic residuals as equality
constraints at each collocation node — a new output slot in the transcription packed functor — and is
a clean follow-on task built on the planned DAE seam (spec §7 table, "Algebraic (DAE) constraints →
transcription/" extension point). It is documented as a follow-on inside Task 8 of this plan.

**Tech Stack:** C++17, existing goss layers (unchanged), GoogleTest, CMake INTERFACE library,
containerised build via `scripts/dev.sh '<command>'`.

## Global Constraints

- Language: **C++17** throughout; no C++20 features.
- `ComposedModel::build(...)` MUST produce a `goss::transcription::OcpProblem<CombinedDyn, CombinedCost>` via an internal `Model::build()` call — the transcription and solver layers are not touched.
- All dynamics and cost lambdas MUST be AD-safe: wrap numeric literals in `T(...)`, use `using std::sqrt;` etc. before transcendental calls.
- New headers live in `include/goss/model/` and are header-only (consistent with the `goss_model` INTERFACE target).
- New test source files are added to `goss_model_tests` in `CMakeLists.txt`.
- `ComponentError : std::runtime_error` is the exception type for all composition errors (unresolved names, duplicate names, cycles, wrong number of states contributed, etc.).
- Verbose, descriptive variable names throughout; type annotations on all non-trivial autos.
- TDD cycle every task: write failing test → run (expect fail) → implement → run (expect pass) → commit.
- All cmake/ctest commands run via `scripts/dev.sh '<ctest --test-dir build -R <pattern> ...>'`. Never build on the host.
- The queue model rebuilt via composition (service_rate as an inline derived quantity from queue_length) is the flagship integration test.
- Algebraic-variable (DAE) flavor is NOT implemented in v1; it is documented as a follow-on.

## Task 2 — `Component` metadata holder

**Purpose:** Define `Component` as a runtime metadata holder (mirroring `Model`'s design) that can
declare: input states (by name — wired from parent), owned states+dynamics (name, bounds, boundary
conditions), inline derived quantities (name + double-typed validation lambda), and cost contributions.
Introduces `DerivedHandle` analogous to `StateHandle`.

**Files touched:**
- `include/goss/model/component.hpp` — new
- `tests/model/test_component.cpp` — grow with declaration tests

**Key design choices in this task:**

- `Component` stores dynamics contributions and derived-expression contributions as
  `std::function<std::vector<double>(const std::vector<double>&, const std::vector<double>&,
  const std::vector<double>&, double)>` (x, u, deriveds, t) → **for validation only** (double path).
  The AD path uses generic lambdas passed to `ComposedModel::build()` and never goes through this
  `std::function` field.
- `DerivedHandle{std::size_t index}` — analogous to `StateHandle`, used to index the `deriveds`
  vector inside user-written dynamics lambdas.
- `input_state(name)` registers a name dependency (the component reads a state owned by another
  component or the parent); returns a `StateHandle` with a sentinel index (`kUnresolvedIndex`), which
  `ComposedModel` replaces with the real index at build-time.
- `add_state(name)` registers an owned state.
- `add_derived(name, validation_double_lambda)` registers an inline derived quantity.
- `set_dynamics(validation_double_lambda)` registers the double-typed validation dynamics for ALL
  states this component owns (the vector size must match the owned state count).
- `set_cost(validation_double_lambda)` registers the optional cost contribution.

**Interfaces produced (component.hpp):**

```cpp
#pragma once
#include <cstddef>
#include <functional>
#include <string>
#include <vector>
#include "goss/model/errors.hpp"
#include "goss/model/handles.hpp"
#include "goss/transcription/transcription.hpp"  // kInf

namespace goss::model {

// Sentinel for unresolved input-state handles (replaced at ComposedModel::build()).
constexpr std::size_t kUnresolvedIndex = std::numeric_limits<std::size_t>::max();

/// Opaque handle to an inline derived quantity, analogous to StateHandle.
struct DerivedHandle {
    std::size_t index;
    constexpr operator std::size_t() const noexcept { return index; }
};

/// Metadata for one owned state within a Component.
struct OwnedStateEntry {
    std::string name;
    double lower_bound;
    double upper_bound;
    double initial_value;
    bool initial_fixed;
    double final_value;
    bool final_fixed;
};

/// Metadata for an inline derived quantity.
struct DerivedEntry {
    std::string name;
    // Validation lambda: (x, u, deriveds_so_far, t) → scalar double.
    // Sized: x uses GLOBAL state indices (post-resolution); deriveds_so_far uses
    // local derived indices in topological order.
    std::function<double(
        const std::vector<double>&,  // global x
        const std::vector<double>&,  // global u
        const std::vector<double>&,  // already-evaluated deriveds (topo order)
        double)> validation_fn;
};

class Component {
 public:
    explicit Component(std::string component_name);

    /// Declare that this component reads a state owned by another component/parent.
    /// Returns a handle with kUnresolvedIndex (resolved at ComposedModel::build()).
    StateHandle input_state(const std::string& state_name);

    /// Declare an owned state with default bounds [-kInf, kInf].
    StateHandle add_state(const std::string& state_name);

    /// Set bounds on an owned state.
    void set_state_bounds(StateHandle owned_state_handle, double lower, double upper);

    /// Pin initial/final value of an owned state.
    void set_initial_state(StateHandle owned_state_handle, double value);
    void set_final_state(StateHandle owned_state_handle, double value);

    /// Register an inline derived quantity for validation (double-typed lambda).
    /// Returns a DerivedHandle for use inside this component's dynamics lambda.
    DerivedHandle add_derived(
        const std::string& derived_name,
        std::function<double(const std::vector<double>&,
                             const std::vector<double>&,
                             const std::vector<double>&,
                             double)> validation_lambda);

    /// Register this component's dynamics (double-typed, for validation only).
    /// The lambda must return a vector of size == num_owned_states().
    void set_dynamics(
        std::function<std::vector<double>(
            const std::vector<double>&,
            const std::vector<double>&,
            const std::vector<double>&,
            double)> validation_lambda);

    /// Optional: register a running cost contribution (double-typed, for validation only).
    void set_cost(
        std::function<double(const std::vector<double>&,
                             const std::vector<double>&,
                             const std::vector<double>&,
                             double)> validation_lambda);

    // Accessors for ComposedModel.
    const std::string& component_name() const;
    std::size_t num_owned_states() const;
    std::size_t num_derived() const;
    const std::vector<OwnedStateEntry>& owned_states() const;
    const std::vector<DerivedEntry>& derived_entries() const;
    const std::vector<std::string>& input_state_names() const;
    bool has_dynamics() const;
    bool has_cost() const;
    // Validation: invoke dynamics_fn with the given vectors (double path).
    std::vector<double> evaluate_dynamics(
        const std::vector<double>& global_x,
        const std::vector<double>& global_u,
        const std::vector<double>& deriveds,
        double t) const;
    double evaluate_cost(
        const std::vector<double>& global_x,
        const std::vector<double>& global_u,
        const std::vector<double>& deriveds,
        double t) const;

 private:
    void check_owned_state_handle(std::size_t local_index, const char* caller) const;
    void ensure_name_unique_in_component(const std::string& name) const;

    std::string component_name_;
    std::vector<OwnedStateEntry> owned_states_;
    std::vector<DerivedEntry> derived_entries_;
    std::vector<std::string> input_state_names_;  // names declared as inputs
    std::function<std::vector<double>(const std::vector<double>&,
                                      const std::vector<double>&,
                                      const std::vector<double>&,
                                      double)> dynamics_fn_;
    std::function<double(const std::vector<double>&,
                          const std::vector<double>&,
                          const std::vector<double>&,
                          double)> cost_fn_;
    bool has_dynamics_ = false;
    bool has_cost_ = false;
};

}  // namespace goss::model
```

## Task 3 — Name resolution and global index mapping

**Purpose:** `ComposedModel` (stub) collects `Component` objects and, on `resolve_names()`, builds
a global name→index map for all states and controls, validates that every `input_state` name is
resolvable to an existing state, every derived name is unique globally, and no duplicates exist.
`ComponentError` is thrown with the offending name on any violation.

**Files touched:**
- `include/goss/model/composed_model.hpp` — new (stub: only `add_component`, `add_control`,
  `resolve_names`, and metadata accessors; no `build()` yet)
- `tests/model/test_composed_model.cpp` — add name-resolution tests

**Interfaces produced (composed_model.hpp partial):**

/// Resolution result for one inline derived quantity after name resolution.
struct ResolvedDerivedEntry {

    std::size_t global_component_index;

    std::vector<std::size_t> dependency_global_derived_indices;  // for topo sort

class ComposedModel {

    /// Register a control variable shared across all components.

    /// Set the mesh for the composed problem.

    std::size_t total_num_derived() const;
    std::size_t num_controls() const;
    /// Returns the global state index for a named state, or throws ComponentError.
    std::size_t global_state_index(const std::string& name) const;
    /// Returns the global derived index (topo order) for a named derived, or throws.
    std::size_t global_derived_index(const std::string& name) const;

    // build() added in Task 5.

    void validate_no_duplicate_derived_names() const;

## Task 4 — Topological sort and cycle detection for inline derived quantities

**Purpose:** When inline derived quantities form a dependency graph (e.g. `b` depends on `a`), they
must be evaluated in topological order inside the assembled dynamics functor. Cyclic dependencies
among inline expressions are a setup error (cyclic implicit relations must use the algebraic-variable
flavor). This task implements Kahn's algorithm over the derived-quantity dependency graph,
raises `ComponentError` on cycles, and exposes the topo-ordered `ResolvedDerivedEntry` list.

**Files touched:**
- `include/goss/model/composed_model.hpp` — add `compute_topo_ordered_deriveds()` private method
- `tests/model/test_composed_model.cpp` — add topo-sort and cycle-detection tests

**Design:** Each `DerivedEntry::validation_fn` is a lambda `(x, u, deriveds_so_far, t)` where
`deriveds_so_far` is indexed by the global derived index in topo order. The dependency set of a
derived entry is determined by which other derived names it `input_derived()` declares. To avoid
requiring users to explicitly list derived-quantity dependencies (which is error-prone), v1 uses an
explicit `component.input_derived(name)` declaration — analogous to `input_state`. This is simpler
than static analysis of the lambda body and consistent with the named-input model.

Add to `Component`:
```cpp
DerivedHandle input_derived(const std::string& derived_name);
// Returns a DerivedHandle with kUnresolvedIndex; the name is added to derived_input_names_.
const std::vector<std::string>& derived_input_names() const;
```

During `resolve_names()`, `ComposedModel` builds the derived dependency graph from the declared
`derived_input_names()` of each component's derived entries (matched to global derived indices),
then runs Kahn's algorithm to compute topological order and detect cycles.

## Task 5 — `ComposedModel::build()`: assemble combined dynamics functor

**Purpose:** Implement `ComposedModel::build(...)` — the core of the feature. It accepts per-component
dynamics generic lambdas and per-derived-expression generic lambdas as explicitly typed template
parameters (same pattern as `Model::build(dynamics, cost)`), assembles them into a single combined
generic dynamics lambda and a single combined cost lambda, and calls an internal `Model::build()`.

**Why this approach works for CppAD:** Generic lambdas are templates on `operator()`, so capturing
them by value in another generic lambda preserves full template instantiation at the CppAD recording
site. No `std::function` is in the hot (AD) path.

**API for the queue example:**
```cpp
// The assembled ComposedModel::build() call:
auto ocp = composed.build(
    // Arg 1: derived-expression lambda for service_rate (inline, topo index 0).
    // Signature: (const std::vector<T>& x, const std::vector<T>& u, T t) -> T
    [BASE_RATE, SLOPE](const auto& x, const auto& u, auto t) {
        using T = typename std::decay_t<decltype(x)>::value_type;
        return T(BASE_RATE) + T(SLOPE) * x[global_queue_idx];
    },
    // Arg 2: dynamics lambda for queue component's owned states.
    // Signature: (const std::vector<T>& x, const std::vector<T>& u,
    //             const std::vector<T>& deriveds, T t) -> std::vector<T>
    [ARRIVAL](const auto& x, const auto& u, const auto& deriveds, auto t) {
        using T = typename std::decay_t<decltype(x)>::value_type;
        return std::vector<T>{ T(ARRIVAL) - deriveds[global_service_rate_idx] };
    },
    // Arg 3: cost lambda.
    [WEIGHT](const auto& x, const auto& u, const auto& deriveds, auto t) {
        using T = typename std::decay_t<decltype(x)>::value_type;
        return x[global_queue_idx] + T(WEIGHT) * u[global_control_idx] * u[global_control_idx];
    }
);
```

The ordering convention for `build()` arguments: **first all derived-expression lambdas in
topological order** (matching `topo_ordered_deriveds_[i].name`), **then one dynamics lambda per
component** in `add_component()` registration order, **then one cost lambda** (combined across all
components, or optional). To keep v1 simple and avoid variadic overloads, `build()` is a set of
overloads covering the queue composition case: 1 derived expression + 1 component dynamics + 1 cost.
A variadic template is documented for future extensions.

**Assembled combined dynamics functor (inside `build()`):**
```cpp
auto combined_dynamics = [
    derived_expr_0,   // captured by value — generic lambda for service_rate
    component_0_dyn,  // captured by value — generic lambda for queue dynamics
    num_states,       // captured by value — std::size_t
    num_deriveds      // captured by value — std::size_t = 1
](const auto& x, const auto& u, auto t) {
    using T = typename std::decay_t<decltype(x)>::value_type;
    std::vector<T> deriveds(num_deriveds);
    // Topo step 0: evaluate derived_expr_0 → deriveds[0]
    deriveds[0] = derived_expr_0(x, u, t);
    // Assemble dx in global state order:
    std::vector<T> dx(num_states);
    auto component_0_dx = component_0_dyn(x, u, deriveds, t);
    // Fill dx at global offsets for component 0's owned states:
    for (std::size_t i = 0; i < component_0_dx.size(); ++i)
        dx[component_0_state_offset + i] = component_0_dx[i];
    return dx;
};
```

Note: `derived_expr_0` receives `(x, u, t)` (no prior deriveds since topo index 0 has no
dependencies). For derived entries with dependencies, the signature is
`(const std::vector<T>& x, const std::vector<T>& u, const std::vector<T>& deriveds_so_far, T t)`.
For v1 uniformity, all derived-expression lambdas receive `deriveds_so_far` as their third argument
(it is empty for topo index 0 entries with no deps), keeping the signature consistent.

## Task 8 — Algebraic-variable (DAE) flavor: follow-on note

**This task is OUT of v1 scope.** It is documented here for the follow-on plan.

The algebraic-variable path (`Component::add_algebraic(name, defining_residual, lower, upper)`)
turns a derived quantity into a real NLP variable with a defining equality constraint
`v − g(x, u, t) = 0` enforced at each collocation node. The implementation requires:

1. **New `OcpProblem` field:** `algebraic_residuals` — a functor `(x, u, alg_vars, t) → vector<T>`
   for the residuals, plus `num_algebraic` count, lower/upper bounds on algebraic variables.
2. **`VariableLayout` extension:** algebraic variables are new slots in the decision vector `z`

3. **Transcription packed functor extension:** Trapezoidal and HermiteSimpson compile functions

4. **`ComposedModel::build()` extension:** collect algebraic entries from components, add to
   OcpProblem, forward through the transcription pipeline.

This is additive (spec §7 "Algebraic (DAE) constraints → transcription/" seam) and does not break
the inline-expression v1 path. It is estimated as a medium-sized follow-on plan (3–4 tasks).
